03 / FROM BROWSE TO BUILD

Follow an order.

Step through the real sequence. Change the scenario to see how failures are handled.

Interactive explanation · no requests sent
BROWSER

A cart follows the browser.

Cart entries live in browser storage and synchronize across tabs on the same origin. They are not a signed-in customer account or a Supabase cart.

localhost:5177, www.barqmech.com and the Vercel alias have separate browser storage. Switching domains does not transfer a cart.

SERVER

A saved order keeps its totals.

The server checks current prices when a new order is accepted. Once saved, that order retains its line snapshots and totals, even if you change catalog prices later.

A retry with the same checkout identifier returns that order. Different details under the same identifier are rejected.

Captured during release acceptance on 20 October 2026. Static evidence, not a view of current customer activity.

How quickly does an edit appear?

A listing save writes to Supabase immediately. Existing storefront tabs refresh on focus/visibility and periodically, roughly every 30 seconds. Checkout rechecks live availability and prices before accepting a new order.

No GitHub commit or Vercel rebuild is needed for a price or status edit.

What is the CSV still used for?

The versioned product and price CSVs seed the catalog and supply offline/build snapshots. They retain 346 products, 2,470 designs and 7,419 size-price rows at release.

They are not an automatic backup of subsequent admin edits. Export/back up live Supabase listings separately. The seed script refuses to overwrite a nonempty live table.

V3 uses the new project bymhkgakvotcqdgcllat. The original ajaugjszvbsdxicswfwx was retained unchanged for recovery. Project IDs are identifiers, not access credentials.

How was the new database initialized?

The fresh V3 project used bootstrap 014 before live-listing/reliability migrations 012 and 013, then the catalog seed and verified history/file migration. Migration 015 later corrected stale-edit responses.

These are already applied. Do not assume sorting all historical SQL files numerically recreates the intended secure V3 setup: older migrations also describe legacy public-write behavior. Use the current release notes and review the target, backup and schema plan before future changes.

PRIVATE

Manufacturing files

DXF
Local design original↓Supabase / product-dxf↓Selected product + design lookup↓Temporary merchant download

342 non-Panel DXFs, 300,106,317 bytes at release. Every migrated file was downloaded again and SHA256-verified.

  • Private bucket; public object access denied.
  • Only the selected design is linked.
  • Download link lasts 14 days.
  • Customers do not receive CAD links.
Panel exception. Panels remain visible and orderable, with their full sizes and prices. Their DXFs are excluded from the new storage. The merchant email says “DXF: Supply manually for this Panel order.” Your team supplies that file manually.
Does “merchant-only” mean the link checks the person’s identity?

No. The signed download is a bearer link: anyone holding its complete URL can download until it expires. “Merchant-only” means it is included only in the merchant email, not that it requires a merchant login.

No real signed URLs or DXFs are embedded in this guide.

Do we still use Google Drive, cPanel or Cloudflare storage?

No. The selected V3 stack is GitHub + Vercel + Supabase + Resend. Cloudflare storage was explored but not adopted. Google Drive folder links are not part of new V3 order emails. Historical systems and archived records are retained for recovery rather than rewritten.

The public product-images bucket exists in the new Supabase project but is empty and unused.

Why does 8.17 sq ft cost Rs. 1,400?

24 × 49 ÷ 144 = 8.16666667 sq ft. Above seven, the area is rounded up to nine. That is two additional square feet: 1,000 + 200 × (9 − 7) = 1,400.

The calculation uses the selected rectangular dimensions, not the photograph’s visible metal coverage. The server repeats the calculation. For reporting, the entire charge is assigned to the first largest-area line; other lines receive zero shipping.

08 / SAVE FIRST, THEN NOTIFY

An order outlives an email.

A delivery failure must not erase a purchase or encourage a duplicate checkout.

DURABLE FIRST

Order saved

Item snapshots, totals, request ID and pending email state.

CUSTOMER EMAIL

“Order received”

  • Order code and purchased configurations.
  • Product pictures and COD totals.
  • Delivery/contact summary and private receipt.
  • No CAD links.
MERCHANT EMAIL

“New order”

  • Customer and fulfillment details.
  • Product pictures, sizes, finish and quantities.
  • Selected non-Panel DXF download.
  • Manual-file notice for each Panel line.
Pending→SentorRetry with backoff→Manual review

When a message fails

The order stays saved. Each recipient’s status and payload are recorded independently. Immediate sending and scheduled hourly retries use stable provider keys to avoid duplicate messages.

Retries have backoff and an attempt cap. Older ambiguous sends move to review rather than being blindly resent beyond the provider’s deduplication window. “Sent” in the order API means provider acceptance; a provider delivery event is separate evidence.

What the receipt reveals

A signed receipt link normally expires after 30 days. Its API returns only the order code, subtotal, shipping, total, payment method and customer-email status.

It does not return the customer’s address, phone, email, private DXF paths or raw notification payload. A six-digit code alone is not proof of access.

Live release test: passed.

Both owner-only test emails show delivered at Resend. Selected Artwork DXF downloaded with a matching checksum; Panel manual notice and customer CAD exclusion were confirmed. All six email-image URLs returned 200. The clearly named test order was marked completed and “DO NOT FULFILL.”

CODE RECOVERY

Keep the previous deployment.

The recovery tag pre-v3-2026-10-19 preserves the earlier GitHub main. A previous Vercel production deployment retains its deployed code/configuration snapshot.

Browse the recovery tag ↗

DATA RECOVERY

A revert does not restore data.

Git/Vercel rollback does not undo database edits or recover deleted files. Keep the original Supabase project, SQL migrations and verified backups.

Local encrypted DPAPI backups include live listings and order/catalog tables. They require the same Windows user to decrypt and are not full PostgreSQL roles/policies or media backups.

Before a release: review the changes, run appropriate tests/build checks, use Preview, confirm required environment settings and recovery, then verify production. Never put a service key in frontend code or a public GitHub file.

  • No direct binary file uploader in admin.
